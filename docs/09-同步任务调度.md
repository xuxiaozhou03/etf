# 09-同步任务调度（pnpm sync）

## 📖 文档概述

本文档描述量化回测系统的**统一同步任务调度**设计：把原分散的多个同步脚本（`scripts/sync-data.ts`、`scripts/sync-etfs.ts`，见 01-项目总览 的目录规划）收敛为**单一入口 `pnpm sync`**。

由**程序**在每次触发时，按 **任务类型 + 任务参数 + 上次完成时间** 逐任务判断是否需要执行，不需要的自动跳过。

**目标读者：** 数据开发工程师、任务/流水线设计者

## 1. 设计原则

| 原则 | 说明 |
| :--- | :--- |
| **单一入口** | 所有同步都通过 `pnpm sync` 触发，不再有 `sync:etfs` / `sync-data` 之分 |
| **程序判断** | 不靠人指定"跑哪个"，由调度器按规则判断每个任务是否执行 |
| **任务可记录** | 每个任务的执行历史（含完成时间、状态、参数）持久化，作为判断依据 |
| **可派生子任务** | 一个任务执行完可以派生子任务（如 ETF 列表 → 每个 code 的 K 线任务） |
| **子任务同规则** | 派生出来的子任务不因"刚被父任务生成"而无条件执行，仍走各自的跳过判断 |
| **统一汇总** | 一次运行结束时汇总：哪些执行了、哪些跳过了、跳过原因 |

## 2. 入口与用法

```bash
pnpm sync            # 驱动调度器：遍历任务清单，逐任务判断是否执行
pnpm sync <task>     # （可选）只跑指定任务（仍走该任务的跳过判断）
pnpm sync --force    # （可选）忽略本次跳过判断，强制执行
```

约定：默认不带参数时，`pnpm sync` 会**按依赖顺序**把所有"该执行"的任务跑一遍，无需外部编排。

## 3. 任务模型

### 3.1 任务定义

```typescript
interface SyncTask {
  /** 任务类型标识，如 'etf_list'、'kline' */
  type: string;

  /** 任务参数（同一类型、不同参数视为不同任务），可空 */
  params?: Record<string, unknown>;

  /**
   * 是否需要执行
   * 由每个任务单独提供规则：一般依据 (type + params + 上次成功完成时间)
   */
  shouldRun(ctx: SyncContext): Promise<boolean>;

  /** 执行任务主体 */
  run(ctx: SyncContext): Promise<void>;

  /**
   * 派生下一层任务（可空）
   * 如 etf_list 执行后 → 为每个 code 组装 'kline' 子任务
   */
  deriveChildren?(ctx: SyncContext): SyncTask[];
}

/** 触发后需要执行的根任务清单（任务 1..N 在此注册） */
const ROOT_TASKS: SyncTask[] = [
  // ...见 §5 任务清单
];
```

### 3.2 任务标识

| 概念 | 含义 | 示例 |
| :--- | :--- | :--- |
| `type` | 任务种类 | `etf_list`、`kline` |
| `key` | 同种任务下区分个体（派生任务用） | `kline` 的 key = `code`，如 `510300.SH` |
| `params` | 影响判断/执行的参数 | 如起始日期、过滤条件 |

### 3.3 执行历史记录（用于"上次完成时间"判断）

现有 Prisma schema（Security / Kline / PeriodReturn）不记录"任务何时跑过"，需新增一张表：

```prisma
/// 同步任务执行历史（判断"是否需要跳过"的依据）
model SyncTaskRun {
  id         Int      @id @default(autoincrement())
  taskType   String   @map("taskType")      // 'etf_list' | 'kline'
  taskKey    String?  @map("taskKey")       // kline 任务 = code；etf_list 可空
  params     String?  @map("params")        // JSON 序列化，同类型不同参数视为不同任务
  status     String   @map("status")        // 'success' | 'failed' | 'running'
  startedAt  DateTime @map("startedAt")
  finishedAt DateTime? @map("finishedAt")   // 上次完成时间（判断依据）
  error      String?  @map("error")         // 失败原因，便于重试决策

  @@unique([taskType, taskKey, params])
  @@map("syncTaskRun")
}
```

> 说明：默认以**最近一次 `status='success'` 的 `finishedAt`** 作为"上次完成时间"。失败记录单独留存，是否重试由各任务规则决定（见 §5 各任务补充规则）。

### 3.4 调度器主流程

> 每次 `pnpm sync` 都是**固定两段式**，顺序不可颠倒：
> **第①段**判断并（按需）执行 `etf_list` → **第②段**再组装/评估各 `[code]_kline`。

```
pnpm sync
  └─ 读取 SyncTaskRun 执行历史
  └─ 【第①段】判断 etf_list 任务
      ├─ shouldRun? ──否──▶ 记录跳过(SKIP + 原因)
      └─ 是
          ├─ 写 running 记录
          ├─ run()：抓ETF列表 → 过滤 → upsert 落库(Security)
          │    ├─ 成功 → 写 success + finishedAt
          │    └─ 失败 → 写 failed + error
          └─（无论 etf_list 执行或跳过，都进入第②段）
  └─ 【第②段】从数据库 Security 表读取 ETF 列表 → 组装 [code]_kline 任务
      └─ 每个 [code]_kline 逐个走同一套 shouldRun/run 判断
          ├─ 写 running → run()（增量拉K线 + 重算阶段收益）→ 写 success/failed
          └─ 跳过 → 记录 SKIP + 原因
```

## 4. 任务派生示例（任务1 → 子任务）

```
pnpm sync 的一次执行（固定两段式）
  第①段  判断 etf_list 是否执行（按规则）
          ├─ 执行 → 抓全量ETF → 过滤 → upsert 落库(Security)
          └─ 跳过 → DB 保持上次内容（记录 SKIP + 原因）
  第②段  从【数据库】Security 表读取 ETF 列表
          └─ 组装 [code]_kline 子任务 → 逐个判断是否执行
```

要点：
- **顺序固定**：先第①段 `etf_list`，再第②段组装 `[code]_kline`。触发 `pnpm sync` 时第一步永远是判断 `etf_list` 任务（执行或跳过），第二步才组装子任务。
- 第②段的 kline 任务源 = **数据库 Security 表现况**。因此 `etf_list` 即使被跳过，第②段依旧会用 DB 里已有的 ETF 列表组装 `[code]_kline` 并逐个判断（源不变，并非"不组装"）。
- `etf_list` 执行与否，只影响 Security 表是否被刷新（刷新后新/更新的 code 在下次第②段出现）。
- Security 需携带 `category / trackingIndex / scale`，作为子任务与后续排行榜的数据基础。
- 每个 `[code]_kline` 子任务**单独**走 shouldRun 判断：`finishedAt` 晚于参考点 T → 跳过；否则增量拉取并重算阶段收益。

## 5. 任务清单（规则逐条补充中）

> 每个任务的"判断规则 / 冷却口径"由需求方逐任务提供后填入下表；尚未提供的标 **【待补充】**。

### 任务1 ｜ 爬虫 ETF 列表

| 项 | 内容 |
| :--- | :--- |
| `type` | `etf_list` |
| 任务内容 | 调用 ETF 列表 API → 过滤（trackingIndex≠null + 规模>3亿 + 同指数取最大）→ 落库 Security（复用 ETFFetcher / syncETFList 逻辑，见 02-数据采集与存储层） |
| 派生 | 完成后从数据库读 ETF 列表，为每个 code 组装 `kline` 子任务（即 `[code]_kline`） |
| 判断规则（跳过条件） | 与 `kline` 同一套「收盘后已完成 → 跳过」规则（2026-09-07 确认，见下方子任务规则） |

### 子任务 ｜ `[code]_kline`（爬取单只 ETF 日 K 线）

| 项 | 内容 |
| :--- | :--- |
| `type` | `kline`，`key` = `code` |
| 任务内容 | 增量拉取该 code 的日 K 线（前复权）→ upsert 到 Kline → 全量重算阶段收益（复用 fetchKlineData / syncETF / PeriodReturnCalculator，见 02） |
| 判断规则（跳过条件） | 见下方「收盘后已完成 → 跳过」规则 |

**「收盘后已完成 → 跳过」规则（需求方 2026-09-07 补充，适用于 `kline`）**

> 取最近一次成功完成的 `finishedAt` 与参考点 T 比较：
>
> | 当前时刻 | 参考点 T | 跳过条件 |
> | :--- | :--- | :--- |
> | 周一 ~ 周五 | 当日 15:00 | `finishedAt` 晚于 T（即 15:00 后已完成）→ 跳过 |
> | 周六 / 周日 | 最近一个**周五**的 15:00 | `finishedAt` 晚于 T → 跳过 |
>
> 等价判断：**需要执行 ⟺ `finishedAt ≤ T`**（尚未在上次收盘点之后跑完）。

伪代码：

```typescript
function klineShouldSkip(finishedAt: Date, now: Date): boolean {
  const T = tradingCutoff(now);            // 见下
  return finishedAt.getTime() > T.getTime();
}
function tradingCutoff(now: Date): Date {
  const d = new Date(now);
  if (d.getDay() >= 1 && d.getDay() <= 5) {
    d.setHours(15, 0, 0, 0);               // 周一~五：当日 15:00
  } else {
    // 周六/周日：回溯到最近的周五 15:00
    const back = d.getDay() === 0 ? 2 : 1; // 周日回 2 天，周六回 1 天
    d.setDate(d.getDate() - back);
    d.setHours(15, 0, 0, 0);
  }
  return d;
}
```

判定示例：

| 当前时刻 | 上次成功完成 | T | 结论 |
| :--- | :--- | :--- | :--- |
| 周四 16:00 | 周三 16:30 | 周四 15:00 | `finishedAt < T` → **执行**（补周四收盘数据） |
| 周四 16:00 | 周四 16:20 | 周四 15:00 | `finishedAt > T` → **跳过**（当日收盘后已跑过） |
| 周六 10:00 | 周五 15:10 | 周五 15:00 | `finishedAt > T` → **跳过** |
| 周六 10:00 | 周五 09:00 | 周五 15:00 | `finishedAt < T` → **执行**（补周五收盘数据） |
| 周日 10:00 | 周五 16:00 | 周五 15:00 | `finishedAt > T` → **跳过** |
| 周一 09:00 | 周五 16:00 | 周一 15:00 | `finishedAt < T` → **执行**（会拉取周一盘中尚未收盘的K线，规则字面如此；如需避免，把触发时刻放到 15:00 后） |

> ⚠️ 注意：该规则按"周一~周五=交易日"简化处理，未考虑**法定节假日休市**（休市日的"当日15:00"并无新K线）。严格化需要交易日历，当前文档按上述字面规则实现，后续可再引入交易日历。
